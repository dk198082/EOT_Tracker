1. Target architecture and consequence

Both the workspace and published app use the same Azure PostgreSQL database d365crm, schema crm, and existing 18 eto_* application tables. No permanent eto_prod_* table set will be introduced. Temporary staging, validation and recovery copies are not additional live datasets.

Workspace actions will affect live production data after this cutover. Both apps will share users, roles, requests, review outputs, files, history, numbering and settings. Routine development tests must run on disposable validation data, not genuine shared records.

The current request table enforces global uniqueness on eto_number. Three pairs of different requests have the same assigned number. A combined dataset cannot store them under the current constraint. Existing assigned numbers must remain unchanged unless the user explicitly changes that policy.

The archive policy is selected, but no records have been archived. Database constraint changes and archival execution require a separately approved, verified migration. All other workspace requests remain active unless a separate dependency decision is approved.

5. Business-data and file safeguards

  • Keep all assigned numbers, including historical numbered drafts. New drafts remain unnumbered until their first successful Submit to ART. The annual allocator must inspect both active and archived historical numbers in the shared dataset and retain concurrency/rollback guarantees.
  • Check split-derived number collisions across both origins and archive states, not only one parent ID. Preserve split relationships and sequences through remapping.
  • Production lacks five scheduling columns. Existing requests without a recorded schedule keep those fields null; do not infer past deadlines or use today's date as their acceptance date.
  • Fix acceptance handling so a previously accepted legacy request with an unknown deadline does not receive a fabricated schedule on rework. Truly first-time ART acceptance still records its selected review durations and calendar date normally.
  • Preserve currency codes, units, historical money/cost/lead-time values, estimated hours, scores and risk explanations. Do not convert currencies, recompute historical prices or treat null risk as Low. Flag legacy values that fail current validators for explicit review.
  • Retain attachment object keys and uploader/request mappings. Verify all imported objects and permissions. If multiple attachment rows reference the same blob, deleting one must not destroy a file still referenced by another record, including an archive.
  • Choose one approved reviewer-default configuration and active runtime marker state. Retain both original settings/markers in the restricted migration audit, with remapped IDs where applicable. Gate automatic role repair/import, pending provisioning, submitter reassignment, reminders and OCR so they cannot undo the merge.

6. Execution stages after approval

Stage 1 — prepare and test without touching live records

Implement the approved archive/legacy-number rule, provenance, API/UI safeguards, stale-client protection and migration tooling against a disposable validation copy. Existing form/action endpoints must consistently use crm.eto_* tables and the writable Azure pool. No local fallback, automatic source overwrite, remote DDL at startup or build-time migration.

Stage 2 — maintenance and final snapshots

Agree a maintenance window affecting both apps. Shut down/pause the published app's business writers and the workspace API/background writers, drain requests and stop other writers. Stopping the workspace workflow alone does not freeze published production. Use supported read-only production access; prove the replica has caught up or obtain an approved authoritative export. Capture a consistent workspace snapshot too, with sequences, fingerprints, file keys, number state and role/default baselines. Preserve private backups of both sources; Azure data needs its own verified backup, not an assumed Replit checkpoint.

Stage 3 — build the combined set in temporary staging

Create an explicitly owned temporary eto_-prefixed staging set in crm. Import both snapshots using the approved mappings and conflict rule. Keep original data intact while validating the result. Reset sequences beyond both sources' captured high-water values, preserve business dates and create all FK/unique protections. Compare transformed source rows to staged rows on every preserved field; ID/provenance/archive changes must match the approved manifest.

Stage 4 — validate and atomically install

Run structural, data and rollback-only CRUD checks, then a single browser workflow pass on disposable validation data. When all gates pass, use a reviewed transactional replacement/swap into the existing crm.eto_* names, handling FK/index/sequence ownership correctly. Do not change unrelated CRM objects. Require all old workers/connections to be stopped; restart only the compatible validated API against the installed shared set. Retain recoverable pre-merge copies for an agreed period.

Stage 5 — user publishing and release

The user publishes the validated build with both environments configured for the same Azure table set. Publishing does not migrate this external Azure data. Keep business writes paused while checking startup, role/identity mappings, all retained requests, archive/duplicate-number handling, dashboards, settings and files. Then enable writes/jobs and monitor the first genuine transactions. All users sign in again; old session token payloads are not merged.

Gate B: Fresh source snapshots and backups verified. Gate C: Shared staged data, constraints, files and workflows pass before installation. Gate D: Both apps point to the same installed set and pass smoke checks before normal writes resume.

7. Verification checklist

  • All 18 live tables use crm.eto_* names and correct CRUD/sequence permissions; no accidental local, staging, backup or separate-production runtime access.
  • All source requests, outputs, comments, files and audit events survive under correct owners/parents; transformed source checksums match and there are no orphaned references.
  • Verified identity merges, preserved roles and approved reviewer defaults match before/after startup and sign-in. Unverified matches cannot grant privilege.
  • Existing drafts retain assigned numbers; new drafts allocate only on successful submission. Concurrent/retried submissions and splitting cannot collide or reuse historical references.
  • Archive/legacy-duplicate behavior works in lists/search, detail views, forms, exports, notifications and calculators. APIs enforce the selected rule for every mutation path.
  • Stale clients or ambiguous numeric links cannot write to the wrong request/user/attachment after rekeying.
  • Test create/edit, comments, attachment upload/preview/download/delete, submit/assign, Engineering/Production/ART Final review, quote/calculator, search/dashboard and logout. Use owned validation fixtures, not genuine request numbers or original files.
  • Confirm expected restrictions by role, historical unknown schedules/risks, rework date stability and preservation of prices/units. No new request/comment deletion UI is implied where none exists.
  • Run type checks, API/integration checks, logs and all-table rollback-only CRUD verification. Record a metadata-only validation report.

8. Rollback and recovery

  • Before live installation, discard only owned temporary staging data if verification fails; both originals stay intact.
  • Before any new shared business writes, restore the verified pre-merge tables and compatible release/configuration if startup/smoke checks fail. Recheck sequences and role/default state.
  • After shared writes begin, both environments may have changed real records. Never restore an older snapshot or reconnect a stale source and silently lose those changes. Pause all writers; use a compatible fix-forward/rollback build or explicitly approved reconciliation of every post-cutover change.
  • Take backups before publishing, review any legacy managed-database prompts, and do not choose data-overwrite operations. No direct DDL/DML against the managed production source is part of this plan.
