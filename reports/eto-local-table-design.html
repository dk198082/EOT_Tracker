18 tables · 181 columns · 19 foreign keys · 42 constraints · 25 indexes

Scope: the local/development PostgreSQL database, public schema. Verified using read-only PostgreSQL catalog queries and the application schema definitions in lib/db/src/schema/. No row data, credentials, session payloads, production data, or external Azure CRM tables are included. No database or application changes were made.

Design notes

  • Column names below are the physical PostgreSQL names. The users.clerk_id column retains its historical name; it is mapped as authId in the application and links the authentication identity.
  • Integer IDs with a nextval(...) default are auto-generated sequence-backed IDs (declared serial in the app). Settings IDs and eto_price_calculator.eto_request_id do not have auto-generated defaults.
  • Most monetary amounts, formula values, percentages, and output estimates are stored as text, not numeric SQL types. Review durations are double precision and scheduling dates are date.
  • Role, stage, decision, risk, and processing-state values are text columns, not PostgreSQL enum types. The current table constraints contain no CHECK constraints; business validation is in the application.
  • The application role values are sales, art, engineering, production, admin, and superuser. The stage values are draft, art-review, engineering-review, production-review, art-final-review, quoted, won, declined, lost, abandoned, and legacy closed.
  • Engineering, Production, and ART Final review due dates are derived in the app from the stored review schedule and acceptance history; there are no additional per-step due-date columns. eto_requests.due_date remains the stored overall due date.
  • eto_requests.eto_number is nullable and unique: a draft can remain unnumbered. Split sequence uniqueness is enforced by a composite unique index.
  • Each Engineering, Production, and ART Final output table allows at most one row per request. Each ETO price-calculator row uses its request ID as the primary key.
  • attachments stores file metadata and a storage key, not file bytes. Audit changes are jsonb; authentication sessions also use jsonb.
  • design_formula_changes.actor_user_id and assembly_formula_changes.actor_user_id are integer actor references without enforced foreign keys. Their actor names and emails are stored snapshots. No user record contents are exported here.
  • Most timestamps have a time zone. sessions.expire is timestamp without time zone. Nullable means database NULL is allowed; this is not necessarily the same as an optional UI field.
