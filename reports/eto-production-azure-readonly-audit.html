Production data is not yet reconciled with Azure

Do not publish the database cutover as-is. The legacy production database contains requests and user/role information not represented correctly in the current Azure dataset. Publishing would change what the app displays and which permissions it grants; the older records would remain in their database but would not automatically appear in Azure.

Audit scope

  • Source: the published app's legacy managed production database, public schema, queried through the read-only production replica.
  • Destination: Azure PostgreSQL d365crm, crm schema, current eto_* application tables.
  • Production has 16 application tables and 168 columns; Azure has 18 application tables and 181 columns.
  • Both datasets were queried read-only. No database rows, schemas, application code, deployment settings or releases were changed.
  • Queries compared row fingerprints and identity signatures without exporting personal names, email addresses or session payloads. Session tokens were not inspected.

Schema and settings considerations

  • Column names match for 15 legacy tables. The production request table lacks engineering_review_duration_weeks, production_review_duration_weeks, art_final_review_duration_weeks, art_review_accepted_date and due_date.
  • A migration needs an explicit deadline/default backfill decision for legacy requests; historical ART acceptance dates must not be invented or reset.
  • The two pricing tables exist only in Azure: eto_price_calculator_settings and eto_price_calculator. Azure currently contains 2 request-specific calculator records.
  • Review-assignment defaults and data-import markers differ. Their user references and bootstrap behavior must be reviewed, not blindly overwritten.
  • Production has 15 stored sessions, of which 1 was active at the audit; Azure has 21, of which 1 was active. Session payloads were excluded from this comparison.

Required decisions before moving production data

  1. Choose whether production should have a separate eto-prefixed table set in crm, or whether the two datasets should be reconciled into one set.
  2. Resolve the three conflicting assigned numbers without silently renumbering or replacing existing requests.
  3. Verify ambiguous/email-only user matches and approve the intended production roles.
  4. Preserve request relationships, comments, history, attachment keys and reviewer ownership; map IDs if merging.
  5. Review defaults, import markers and legacy deadline handling.
  6. Take a final consistent snapshot during an agreed write pause, migrate with rollback protection, then verify real production forms/actions before publishing the switch.

This is a read-only point-in-time audit, not a data migration or continuous synchronization. Production queries use a replica; counts and records may change after the audit. A separate production table set is a possible way to preserve IDs, numbers and roles without overwriting the workspace dataset, but it has not been implemented or approved.
